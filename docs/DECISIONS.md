# OFFGRID: Trade-offs, Mocks and Legal Flags (Phase 0)

## 1. Trade-off summary

| # | Decision | Chosen | Rejected | Why |
|---|---|---|---|---|
| D1 | Backend language | **Node + TypeScript** | FastAPI (Python) | The recommender, XP and settle-up must run *offline in the browser* and *authoritatively on the server*. With TS, that is one package (`@offgrid/core`) and one test suite. Python would mean writing it twice. Python is worth revisiting only if real ML models arrive (served as a separate microservice). |
| D2 | Database | **SQLite now, Postgres + PostGIS later**, via the **Kysely** query builder | Postgres from day 1; Drizzle | Judges and teammates run `npm run dev` with no Docker. Kysely (changed from Drizzle in Phase 2) writes the same typed queries for SQLite and Postgres, and migrations live in code, so switching is a dialect change. Geo queries will sit behind one module. Cost: no true spatial index in MVP; bbox prefilter + haversine is fine below ~50k POIs. |
| D3 | "ML" claim | **Rule-based scoring with tunable weights now; learning-to-rank later** | Training a model now | There is no interaction data yet, so a trained model would be fiction. Honest pitch: weights live in `scoring-rules.json`; once trips + ratings accumulate, we fit weights by logistic regression on "picked / completed / rated ≥4". Moderation uses real heuristics (trigram + distance dedupe, trust-weighted voting, rate anomaly checks). |
| D4 | Planner location | **Client-side (core in browser)** | Server-only | Works in airplane mode in Kheerganga. Server mirror exists for share links and clients without a pack. |
| D5 | Offline writes | **Outbox + client UUIDs + idempotent PUT** | CRDTs / full sync engine | Writes are mostly append-only (trips, submissions, reports). A CRDT is overkill. Conflicts: last-write-wins on trip drafts, which only the owner edits. |
| D6 | Chat transport | **SSE + POST** | WebSockets / Firebase | Low volume, works through proxies, no vendor. Upgrade path: Socket.IO. |
| D7 | Maps / offline tiles | **Leaflet + OSM, bounded tile cache (zoom ≤ 14 around saved trips)** | Mapbox / Google | No paid keys. **OSM tile policy prohibits bulk prefetch**, so for a "download region" feature at scale we'd self-host vector tiles (Protomaps PMTiles file on object storage, ~₹0 hosting). For the hackathon: cache what the user viewed + the trip corridor only. |
| D8 | Hardware | **ESP32-S3 + SX1262 LoRa (865–867 MHz) + GPS, BLE to phone** | GSM module / satellite | GSM fails where there is no network, which is the whole point. Satellite SOS (e.g. phone-satellite features) is expensive and device-limited. LoRa 865–867 MHz is **licence-exempt in India** (low-power, per the WPC exemption) and reaches 2–10 km line-of-sight in hills. |
| D9 | Companion matching scope | **Trip-scoped travel buddy finder** | Open "people browsing" | Matching only exists in the context of a destination + dates. No swiping, no photos-first cards, no "nearby people" radar. This keeps it clearly non-romantic and reduces stalking risk. |
| D10 | XP integrity | **Server-awarded, append-only `xp_events` ledger** | Client-side XP | Leaderboards are worthless if the client decides XP. The ledger lets us audit and re-derive scores after fixing a cheat. |
| D11 | Leaderboard default | **Opt-in, monthly seasons** | Everyone public, all-time | Privacy (activity patterns reveal where people are) + new users can compete. |
| D12 | Money | **Integer paise** | Floats | `0.1 + 0.2` problems in settle-up. |
| D14 | Sessions | **15-min JWT access token in memory + rotating opaque refresh token in an httpOnly, SameSite=Strict cookie**; reusing a spent refresh token revokes the whole login family | Long-lived JWT in localStorage | XSS can't read the cookie, and a stolen refresh token is detected on first reuse. Cost: two tabs refreshing at the exact same moment can log each other out; the client de-duplicates refreshes within a tab, and a short grace window can be added if it shows up in practice. |
| D15 | Trip XP grading | **Server-side GPS plausibility** (reached the place, enough points, long enough, no teleports or future timestamps) → verified 100% / partial 50% / manual 25% (max 2 manual a month). Badges count only verified/partial trips | Trusting the client; photo proof | Cheap, works offline (points are buffered), and explainable to the user. **Limit:** GPS can be spoofed on a rooted phone. The mitigations are the manual cap, the leaderboard opt-in and community reports in Phase 6, with beacon-signed tracks in Phase 7. |
| D16 | Account deletion | **Immediate hard delete** (cascades to trips, GPS, XP, badges, sessions, consents), password required | 30-day soft delete | Simpler and more privacy-protective under DPDP. Requiring the password stops a stolen 15-minute token from deleting an account. |
| D17 | POI data | **Real OpenStreetMap data** (821 points imported by `scripts/import-osm.mjs`) plus a small curated layer (government-run HPTDC stays, annual fairs) | Inventing sample businesses | Real names and locations are more useful and honest. OSM rarely has prices or "women-friendly" information, so those come from the curated layer and community submissions. ODbL requires attribution, which is shown on every map and list. |
| D18 | Community verification | **Trust-weighted votes**: weight = 0.3 + trust/100. Verified at score ≥ 2.0 with ≥ 3 upvotes; total flag weight ≥ 0.6 sends it to a moderator. Once a moderator decides, votes no longer change the status | Simple vote counts | **Limit (Sybil attacks):** until ID verification (Phase 5), about 7 fresh accounts could verify a fake place. Mitigations: signup rate limits, 5 submissions a day, flags beat upvotes, moderators can reject (which revokes the contribution XP), and verification only adds a point of interest; it never moves money or reveals people. |
| D19 | Sensitive places | **Fixed-grid fuzzing** (~2 km cells) for "approximate" places; exact pin only for the contributor and moderators; photos re-encoded server-side, which strips EXIF/GPS | Random jitter | Jitter can be averaged away by looking at the place many times; a fixed grid can't. |
| D20 | Offline writes | **One outbox path for everything**: every submission (with photo blobs) goes to IndexedDB first, then uploads. Client-generated UUIDs for places and photos make retries idempotent. Retries run at start-up, on reconnect and every 60 s | Separate online/offline code paths | One path is easier to trust and test. 4xx responses are kept and shown to the user rather than silently dropped. |
| D21 | Weather | **Open-Meteo behind a `WeatherAdapter`** (mock for tests/demos), queried at two elevations per trip (base town and highest point), cached 1 h on the server and saved on the phone | Calling a weather API from the client | Mountain weather differs hugely with height (on 23 Oct: Manali +13.5 °C, Hampta Pass −9.9 °C at the same coordinates). Server caching keeps us well inside the free quota. **Licence:** Open-Meteo's free API is for non-commercial use and needs attribution (shown on the Weather tab); a commercial launch needs their paid plan or an IMD partnership behind the same adapter. |
| D22 | Warnings | Rule-based, data-driven thresholds (`safety-rules.json`), **grouped per kind** ("Hard frost, 7 days, worst −17 °C") and tied to the route (rain + river crossings = "streams will be high") | One line per day | The first live test produced 8 near-identical frost lines that hid the one snow day; grouping fixed it. |
| D23 | Hazard reports | **Live immediately, labelled "Traveller report", auto-expire by kind** (12 h lightning to 72 h landslide); "Still there" extends (capped at 7 days), two "It's gone" or the reporter clears it | Moderation before publishing | A warning that waits for review is useless. False reports cost little because they expire; repeated abuse is handled through Phase 6 reports and blocks. |
| D24 | Alerts | **Computed on the phone** from the region pack and saved forecasts; device notifications for severe alerts via the Notification API, once per alert | Server push (Web Push) | Works with no signal, which is exactly when it matters, and needs no push infrastructure. **Limit:** notifications only fire when the app runs. Web Push (VAPID) comes with the beacon relay in Phase 7. |
| D25 | Women-only matching | **Unlocked only by an ID-verified female gender, and enforced in both directions.** Verified gender always overrides self-declared | Self-declared gender | Otherwise a man could tick "women only" and get a list of women. Gender is never displayed. |
| D26 | Contact sharing | **Server-side masking** of phones, emails, UPI IDs, social handles and messenger links until **both** people opt in. Numbers are only ever *verified* phones | Free-form chat | Moving off-platform early is the usual start of scams and harassment. The walkthrough found the "WhatsApp" keyword eating half a number, which is now fixed and tested. |
| D27 | Chat transport | **Server-sent events read via `fetch`**, not `EventSource` | EventSource; WebSockets | EventSource can't send an Authorization header, and a token in the URL leaks into logs. The compression middleware skips `/stream` routes so gzip can't buffer messages (tested with `Accept-Encoding: gzip`). |
| D28 | KYC | **DigiLocker (MeriPehchaan OAuth + PKCE) behind `KycAdapter`**, with a clearly labelled simulated consent page in demo mode. One-time `state` bound to the user expires in 10 minutes; the year of birth must match the profile | Collecting Aadhaar numbers ourselves | Only UIDAI-licensed entities may do Aadhaar eKYC; DigiLocker gives verified data **with the user's consent**. We keep document type + last 4 + gender only. |
| D29 | Leaderboard fair play | **A second check, separate from the XP grade.** At completion each trip is marked leaderboard-eligible or not: simulated tracks, GPS windows that overlap another of your trips, more than 2 finishes in 24 h, and trips with no track are kept off the boards. The reasons are shown to the owner | Banning or docking XP | A flagged trip still counts towards your own level and badges, so honest edge cases (two short hikes in a day) aren't punished, but nobody climbs a public board with them. Monthly seasons give newcomers a fresh start. |
| D30 | Challenges and streaks | **Monthly challenges and a streak bonus, paid into the XP ledger with unique keys** (`challenge:id:season`, `streak:season`). They count only verified trips that passed fair play | Weekly quests; counting every trip | Challenge XP shows on the XP board, so it must meet the same bar (the walkthrough caught a simulated trip completing "Double up"). XP already paid stays when a contribution is later rejected; it was earned in good faith that month. |
| D31 | Buddy ratings | **1–5 stars plus optional tags, only after the rater's trip has ended, one per chat (editable).** The rated person sees only their average. Up to 10 trust points | Public written reviews | Written reviews invite retaliation and defamation risk. Gating on a finished trip stops strangers rating each other off a single message. |
| D32 | Expense splitter | **Local-first, in IndexedDB on one phone.** Integer paise, greedy settle-up (at most n−1 payments), UPI deep links, "Mark paid" recorded as a counter-expense | Server-side shared ledger | Bills get split where there's no signal, and friends shouldn't need accounts. OFFGRID never moves money (no RBI licence needed), and amounts never leave the phone unless the user shares the summary. Syncing between phones is a later stretch. |
| D33 | Compare mode | **Pure client-side `comparePlaces`** reusing the recommender, budget and season logic, with a "better for you" tick per row | A static spec sheet | Comparing for *this* traveller's budget, month and fitness is the point. It works offline like the planner. |
| D34 | Beacon packet | **34-byte binary v1, HMAC-SHA256 truncated to 80 bits, no encryption, hop count outside the MAC** | JSON; AES-encrypted payloads; full 256-bit MAC | Fits one LoRa frame at SF9 (~0.3 s). Relays need to read and prioritise an SOS, so it isn't encrypted; the MAC stops forgery. 80 bits is plenty against online forgery with a rate-limited endpoint. A shared test vector, cross-checked in Python, keeps TypeScript and C++ in step. |
| D35 | Replay protection | **Unique (beacon, seq) plus a 64-packet window behind the highest seq**; seq stored in flash; re-pairing resets both | Timestamps | Beacons may have no GPS time. Mesh hops reorder packets, so a strict "must increase" rule would drop real SOS packets. A cancel only ends an SOS if no newer SOS exists. |
| D36 | Contact alerts | **One SMS at start and one at end, plus a token-protected live page** that dies 72 h after the end. SMS behind an adapter; the mock is refused in production | An SMS per location update; a contact app | An SMS every 30 s buries the first one and costs money. Contacts need no app or account. The page shows only what helps a rescue. |
| D37 | Phone SOS offline | **5-second countdown (not hold-to-press), then PUT with a client UUID; if that fails, it queues in the outbox**; the beacon (over Bluetooth) is told first | Hold-to-press only; blocking until online | A countdown is accessible and still stops pocket presses. Idempotent ids mean the queued retry can't create a second SOS or restart a cancelled one. 112 is always shown first. |
| D38 | Firmware roles | **One sketch: beacon + relay + optional Wi-Fi gateway + BLE link to the phone**; pairing over USB serial (Web Serial) | Separate gateway firmware; BLE pairing | Fewer things to flash and explain. USB pairing means the key goes only to the device physically in your hands. **Limit:** continuous receive gives about a day of battery; duty-cycled RX is next. |
| D39 | Place photos | **Wikimedia Commons, freely licensed only, credit shown on every photo**; hand-picked from a candidate list; served from Wikimedia's thumbnail servers and cached by the service worker once seen | Google Places photos; stock sites; scraping Instagram | Google's photos need a paid key and forbid caching. Commons photos are free to reuse **with attribution**, which the UI always shows (author, licence, link). Hand-picking avoids off-topic search hits (birds, a Swiss town called Chur). |
| D40 | Trail lines | **Shortest walking route on OSM paths between geocoded trailheads and destinations, rejected if it detours (>1.3× half the trek's distance) or can't snap within 700 m** | Hand-drawn lines; a routing API (paid keys); straight lines | The lines are real mapped trails, ODbL-attributed, offline in the pack (about 30 KB). The quality gate dropped Indrahar and Bhrigu, which detoured over roads because OSM is missing trail sections. **No line beats a wrong line in the mountains.** |
| D13 | Scope for SIH | **Must-have:** planner, profile/XP/mascot, nearby offline, hidden places, weather/hazards/safety card, beacon. **Should-have:** matching + chat + mock KYC, leaderboard, expenses. **Nice:** compare, unequal splits, liveness. | Building everything evenly | 10 features done 70% demo worse than 6 done 100%. The demo flow (Phase 8) only needs the must-haves to shine. |

## 3. Legal and privacy flags ⚠️

1. **DPDP Act 2023 + DPDP Rules 2025.**
   - Notice + **itemised consent per purpose** (KYC, location, matching), recorded in `consents`, withdrawable anytime.
   - **Data minimisation:** birth year not DOB; ID last4 + provider reference, never the full ID number or document image; selfie deleted right after the liveness check; GPS tracks summarised after 90 days.
   - **Rights:** export (`GET /me/export`) and erasure (`DELETE /me`) built in from Phase 2.
   - **Security safeguards:** PII encrypted at rest (AES-256-GCM), TLS in transit, access logs for admin actions.
   - **Breach duty:** a written breach-response note in PRIVACY.md (notify the Data Protection Board and affected users).
   - **Children:** the Act needs verifiable parental consent for under-18s, and the matching feature is unsafe for minors anyway → **18+ only**, enforced at signup.
2. **No background-check claims.** "ID Verified" means *"this person proved their identity to DigiLocker"*, not that they are safe. The UI will say exactly that, and the safety tips still apply to verified users.
3. **Gender-based filters** (women-only matching) use self-declared gender. This is a safety feature, but self-declaration can be abused. Mitigation: women-only matching requires gov_id tier (which carries gender from the document, with consent), plus report/block.
4. **Location sharing** is off by default, is per-trip, and expires when the trip ends.
5. **User photos of people**: the upload guidelines ask for no identifiable strangers; there's a report flow.
6. **Sensitive / sacred sites**: location fuzzing + community flag "should not be public". Respects local communities and the Forest Rights Act context.
7. **Radio:** beacon must stay within the 865–867 MHz licence-exempt band and power limits; documented in HARDWARE.md. The SOS is **not** a replacement for 112; the UI always shows 112 first.
8. **UPI deep links** in settle-up just open the user's UPI app. We never process payments, so no RBI PA licence is needed.
9. **Map data:** OSM is ODbL. We must show "© OpenStreetMap contributors" attribution, and if we publish an extract of community POIs mixed with OSM, it must stay under ODbL.
